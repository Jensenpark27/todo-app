# 배포

사용자가 배포를 요청하면 아래 순서대로 진행한다. 설명과 보고는 한국어로 한다.

## 1. 현재 상태 확인
- `git branch --show-current`로 현재 브랜치를 확인한다.
- `git status --short`와 `git diff`로 바뀐 내용을 확인한다.
- 바뀐 내용도 없고 push할 커밋도 없으면, 배포할 것이 없다고 알리고 멈춘다.

## 2. 기능 단위로 커밋
- 바뀐 내용을 기능별로 나눈다. 여러 기능을 한 커밋에 섞지 않는다.
- 파일 단위로 `git add <파일>`을 해서 기능마다 따로 커밋한다. `git add .`나 `git add -A`는 쓰지 않는다.
- `package-lock.json` 등 요청과 무관하게 바뀐 파일은 커밋에 넣지 않고 사용자에게 알린다.
- 커밋 메시지는 **한국어 한 줄**로 쓴다.
  - 예: `할 일을 전체/진행 중/완료로 거르는 상태 필터 추가`
- 커밋하기 전에 `npx eslint .`와 `npm run build`가 통과하는지 확인한다. 실패하면 커밋하지 말고 원인을 알린다. 환경 문제로 확인할 수 없으면 그 사실을 보고에 적는다.
- 시스템이 알려 준 커밋 서명 문구(Co-Authored-By 등)가 있으면 메시지 끝에 붙인다.

## 3. 브랜치에 따라 올리기

### main 브랜치일 때
- `git push origin main`으로 올린다.
- PR은 만들지 않는다.

### 기능 브랜치일 때
1. `git push -u origin <브랜치>`로 올린다. 네트워크 오류는 최대 4번까지 간격을 늘려 다시 시도한다.
2. main을 대상으로 PR을 만든다. 제목과 설명은 한국어로 쓴다. 저장소에 PR 템플릿이 있으면 그 제목 구조를 따른다.
3. PR을 main에 병합한다.
4. 병합 결과(PR 링크, 병합 커밋)를 알린다.

## 주의
- GitHub 작업은 `gh` CLI가 아니라 GitHub MCP 도구(`mcp__github__*`)로 한다. 도구가 안 보이면 ToolSearch로 불러온다.
- push나 병합이 권한 오류(403 등)로 막히면 같은 명령을 반복하지 말고, GitHub 재연결이 필요하다고 알린다.
- 병합이 충돌이나 필수 검사 실패로 거부되면 강제로 밀어붙이지 말고 상황을 알린다.
- force push는 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
- 사용자가 따로 요청하지 않은 기능은 이 과정에서 추가하지 않는다.
